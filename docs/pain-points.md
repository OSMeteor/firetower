# 外部痛点材料

本文是 [scale-plan.md](scale-plan.md) 的附录，原先是该文的「收集的痛点」一节。方案和阶段以 scale-plan.md 为准，这里只保留材料和它们对应到方案的哪一处。

这些是公开技术分享里的材料，不是本仓库的压测。文中的百分比和耗时以原文为准。阅读时分成三类：

- **生产事故**：发生过故障，原文写了影响和过程。
- **架构瓶颈**：扩容时发现原设计撑不住，随后改了结构。
- **工程问题**：团队公开讨论过，不能据此说一定造成过线上事故。

对 Firetower 更需要防的是重连风暴、热点 Topic、队列积压、故障后的路由恢复、消息顺序和状态一致性。一条 TCP 长连接能写多少字节，不是这批材料里的主要问题。每条材料对应的现有函数和改法见 [scale-plan.md](scale-plan.md) 的「当前代码与改法」。

## 生产事故

**Discord，2026-03-25，语音服务降级约 3 小时。** 缩容时 Kubernetes 终止了还持有会话的 Pod，会话没能在终止期限内迁走。约 17% 的会话被异常终止，Gateway 通知客户端重连；原有的会话启动限流不匹配新的规模，部分节点内存耗尽。重连再冲击语音服务，连接池组件的队列堆积，服务发现也没能及时更新，健康节点被分到更多流量。来源：[Behind the Scenes of the 3/25/26 Voice Outage](https://discord.com/blog/behind-the-scenes-of-the-3-25-26-voice-outage)。

落到方案：缩容先排空。重连使用指数退避和随机抖动。每台 Gateway 限制订阅重放速率，Manager 有全局恢复队列。恢复要单独压测，不能只压正常流量。阶段 1A、2。

**闲鱼，早期 IM 的丢失、重复和状态错误。** 消息身份是 `SessionID + SeqID + Version`，客户端还会预生成临时 Version。两人同时发送时，新消息会被当成本地已有消息滤掉，或因 Version 不同显示两次。服务端若只根据「连接还在」就认为已经送达，会出现人在线但消息没到端上。后续用 UUID、客户端去重、全链路追踪和对账。来源：[闲鱼亿级 IM 消息系统的可靠投递优化实践](https://www.cnblogs.com/imteck4713/p/15336064.html)。

落到方案：`FireHeader` 里的 id 只是传输 id。业务 `MessageID` 从第一次接受起保持不变，客户端按它去重。归可靠消息层，框架只透传正文。

**闲鱼，长连接下行成功仍不等于用户收到。** 原文给出的原长连接下行成功率约 97%；其定义的补偿到达耗时约 60 分钟，不是所有消息的平均延迟。问题包括连接被判断为正常但传输已断、在线状态滞后、客户端收到后落库失败。来源：[闲鱼消息及时性优化实践](https://segmentfault.com/a/1190000040839544)。

落到方案：分开统计服务端已接受、客户端已确认、用户已读。可靠聊天要有端上确认和序号缺口检测。归可靠消息层。

**Meta，跨地域聊天乱序。** 工程回顾里写过：跨数据中心复制延迟导致用户先看到通知、看不到内容，也出现过聊天消息乱序。同一地域内正常，不能代表跨地域也一致。来源：[Engineering at Meta](https://engineering.fb.com) 关于历史基础设施演进的回顾，具体文章链接待补。

落到方案：一条 TCP 内部的顺序不够，Bucket 的多个消费者和多 Manager 都会打乱先后。序号由可靠消息层在调用 `Publish` 之前分配，客户端按序号重排并补缺口。

## 架构瓶颈

**Discord，2023-10，超大社区的 Relay。** 为 Midjourney 这类社区把单个 Guild 的扇出拆到多个 Relay，但每个 Relay 保存完整成员列表。成员到百万级后，同一份列表占多份内存；新建 Relay 要从主进程复制大量成员，Guild 进程会停顿几十秒。扩容动作本身把房间变慢。后来改为只同步该 Relay 需要的成员。来源：[Maxjourney](https://discord.com/blog/maxjourney-pushing-discords-limits-with-a-million-plus-online-users-in-a-single-server)。

落到方案：Manager 只保存 `Topic → Gateway`，Bucket 只保存 `Topic → 本机连接`。权限和成员在独立服务，按需缓存。当前代码已经是这个边界，保持即可。

**Discord，同一轮优化里的主动 / 被动会话。** 早期把用户有权看到的更新都推下去，即使用户没打开该社区。大型社区里约 90% 的用户—社区连接是被动的，改成被动会话不收全量流之后，扇出明显下降。来源同上。

落到方案：没打开该房间的在线连接，不推可延迟的状态流。可靠聊天通知仍按送达规则走。这是订阅上的一个标志，阶段 1B。不能把游戏社区的被动策略直接套到必须送达的企业消息上。

**钉钉，2022，消费者加机器但吞吐不增加。** RocketMQ 的 Queue 数少于消费者时，多出来的机器分不到负载。发布或实例异常触发 Rebalance 时，有的 Queue 被多个消费者同时订阅，有的几十秒没人消费，表现为乱序和未读状态错误。来源：[RocketMQ 在钉钉 IM 系统中的应用实践](https://developer.aliyun.com/article/1122862)。

落到方案：`Hash(Topic) % Manager 数` 不能单独作为扩容。一个 Topic 在一个 RouteEpoch 里只有一个主人。阶段 3 改为向全部 Manager 登记、哈希只决定发布，绕开主人切换。

**钉钉，系统通知打满单个分片。** 存储若按发送者用户 id 分片，系统账号群发会打在同一个分区上。集群总 CPU 不高，不代表这个分区没满。来源：[5 亿用户如何高效沟通？钉钉 DTIM 架构揭秘](https://www.infoq.cn/article/nfyeb9cf6ql3mqo8cful)。

落到方案：容量 WARN 要落到 Topic 和具体 Gateway 的写出队列。总写入满了才加 Manager；只有一个 Topic 满，先做 1B 的热点隔离。阶段 1A 的计数，阶段 1B、3。

**企业微信，2021，万人群的扩散。** 一万人各发一条、若按每人一份扩散，量级会到一亿次。继续加 goroutine 会把存储和旁边的业务压垮。他们按群限制并发，大小群分开的 Worker，批量写，并降级大群里不重要的控制事件。分享中的示例是小群 Worker 250、大群 Worker 30。来源：[企业微信的 IM 架构设计揭秘](https://cloud.tencent.cn/developer/article/1849308)。

落到方案：每个大房间有自己的速率、并发上限和队列，不跟小房间抢同一条工作池。阶段 1B。

**企业微信，同一篇里的已读覆盖。** 「读出列表、改一份、整份写回」时，两人同时已读会丢掉其中一人的记录。他们改为追加、异步重试和合并，并报告相关写入量减少约 44%。来源同上。

落到方案：Gateway 断线清理和重新订阅同时发生时，用 `GatewayID + SessionEpoch` 区分连接代际。只靠一把互斥锁不能认出「这是旧会话的退订」。阶段 2 的握手键里带连接代数。

## 工程问题

**钉钉，离线积压把客户端打满。** 用户几天不在线，积压上万条。登录后逐条推会占满手机的 CPU、内存、流量和电量。积压超过阈值后改为 Rebase：先通知同步位点，客户端取最新状态，历史按需加载。同一篇也讨论了重试造成的重复，以及旧消息晚到造成的乱序。来源同上，DTIM 架构揭秘。

落到方案：`sendOut` 满了就丢，只保护本机，不是可靠同步。状态事件可以丢或只留最新值。可靠聊天落后过多时停止逐条推，改为按序号补拉。框架侧是 1B 的缺失提示，补拉归可靠消息层。

**微信早期收发。** 这是架构分享，不是事故复盘。逻辑层先处理并存储，再经长连接或系统推送通知客户端，客户端按序号拉取。手机进后台后，操作系统可能停掉应用的网络，长连接不能代表用户收得到。来源：[十年前的微信消息收发架构](https://developer.cloud.tencent.com.cn/article/2409784)。

落到方案：移动端要有系统推送和增量同步。WebSocket 在线只表示这条连接还在。可靠消息层的消息日志，加上业务侧的推送通道。

**vivo，2025，未读数把查询打重。** 打开应用时对几十个群做 `COUNT(*)`，用户很久没读时扫描行数很大。产品上未读只显示到 `99+`，再用有界结构降低计算。来源：[vivo：百万级群聊的设计实践](https://www.cnblogs.com/vivotech/p/18740478)。

落到方案：未读统计不进 Firetower 的扇出路径。放在 IM 业务层，用游标和有界展示。

**Discord，2024，换压缩算法后包变大。** 用 Zstandard 替换 zlib 的初期试验里，同类消息从约 250 字节变成 750 字节以上，因为丢掉了原来跨消息的压缩上下文。改回流式压缩后，才报告 Gateway 流量下降近 40%。来源：[How Discord Reduced Websocket Traffic by 40%](https://discord.com/blog/how-discord-reduced-websocket-traffic-by-40-percent)。

落到方案：改 `FireHeader`、序列化、压缩或对象池时，用真实负载做 A/B。同时看 CPU、内存和端到端延迟。压缩率变高本身不算优化。

**Discord，2026，追踪把热点打慢。** 为了查大型社区延迟加上更细的分布式追踪后，解析追踪上下文占用了热门 Guild 的处理能力；埋点延伸到会话扇出路径时，CPU 又增加约 10 个百分点。同一分享里还提到部分用户连上受影响 Guild 进程的时间接近 16 分钟。来源：[Tracing Discord's Elixir Systems (Without Melting Everything)](https://discord.com/blog/tracing-discords-elixir-systems-without-melting-everything)。

落到方案：百万级扇出的热路径上只留采样、批量计数和慢路径追踪，并单独看监控自己的开销。全阶段。

**Slack，2023，Channel Server 的恢复。** 这是架构分享，不是事故复盘。频道按一致性哈希放在 Channel Server 上，另有哈希环组件 CHARMs 和服务发现。失效的 Channel Server 可以在约 20 秒内被替换到能接流量的状态，Gateway 有区域排空。来源：[Real-time Messaging](https://slack.engineering/real-time-messaging/)。

落到方案：哈希只决定 Topic 放在哪。阶段 2、3 把恢复耗时作为验收指标。
